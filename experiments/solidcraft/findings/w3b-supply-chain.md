## 1. Method

Every claim below cites the exact file checked (license-inventory §7 protocol: date ·
source · method · recorder · confidence). Canonical texts used for comparison:

- Apache-2.0: `https://www.apache.org/licenses/LICENSE-2.0.txt` fetched 2026-10-19,
  sha256 `cfc7749b96f63bd31c3c42b5c471bf756814053e847c10f3eb003417bc523d30` (202 lines).
- MIT: the standard text as shipped by serde 1.0.229
  (`~/.cargo/registry/src/index.crates.io-…/serde-1.0.229/LICENSE-MIT`), compared
  word-for-word (whitespace-normalized).
- Per-crate licenses: the crates' **own `Cargo.toml` `license` field**, read at the exact
  locked version — from the registry cache (`~/.cargo/registry/src/…`, the published package
  sources themselves) for registry crates, and from the pinned tree for
  path/vendored crates. The crates.io sparse index serves **no** license field (verified —
  fetches of `index.crates.io/ca/dm/cadmpeg-core` return version records without `license`),
  so manifests are the first-hand source, stronger than index metadata.
- Dependency enumeration: **programmatic**, not hand-copied —
  `cargo metadata --locked --format-version 1` in `experiments/solidcraft/harness/`
  (rc 0, no compilation; it only refreshed the sparse index and downloaded a few crate
  sources), parsed by [`python/w3b_closure_audit.py`](../python/w3b_closure_audit.py)
  (in-tree driver), cross-checked version-by-version against `harness/Cargo.lock`.
  Dev-dependencies excluded; build-dependencies included and classified; target-gated
  (cfg) edges classified per host triple `x86_64-unknown-linux-gnu`. `cargo tree` was
  attempted (empty output with `-p solidcraft-sketch`) and abandoned in favour of the
  metadata graph, which the lock cross-check validates (137 lock packages = 136 closure-2
  packages + the harness root — every lock entry accounted for).

### 3.2 What adapting/porting vendored-patched code obligates (Apache-2.0 © RICOS)

If we port any vendored-patched code (the realistic case is the kernel-side candidates
#2/#3/#4, e.g. history-tracking concepts — though W2's recommendation was design-level
adapt with kernel-level *reference*, which minimizes this):

1. **Retain the Apache-2.0 license text** for the ported files' provenance.
2. **§4(b) prominent change notices on modified files** — SolidCraft's own marker
   convention satisfies this for their patches; our changes must be equally prominent
   (keep their `SolidCraft:` markers *and* add ours, or replace with an explicit scheme).
3. **§4(d) NOTICE propagation** — carry the attribution notices (© RICOS Co. Ltd.;
   SolidCraft modifications per vendor/README.md) in our third-party notices.
4. **Dual attribution chain**: original © RICOS (truck) → SolidCraft's documented patches
   (vendor/README.md + ATTRIBUTION.md) → our changes. vendor/README.md is precise enough
   to serve as the patch list we cite.

## 7. Dual-license election: recommendation

`MIT OR Apache-2.0` lets the adopter pick one term per component. For our context
(extension GPL-3.0-or-later; host GPL-2.0-or-later via "or later" combined distribution;
license-inventory §8 chain):

- **MIT election**: obligations = retain the copyright + permission notice ("Copyright (c)
  2026 SolidCraft contributors") in the shipped notices/ported files. Simplest bookkeeping;
  MIT is compatible with both GPL-2.0+ and GPL-3.0+ directly.
- **Apache-2.0 election**: obligations = provide the Apache-2.0 text, propagate their
  NOTICE attribution content (§4(d)), and carry prominent change notices on any files we
  modify (§4(b)); Apache-2.0 enters **only** through the GPL-3.0-or-later path (incompatible
  with GPL-2.0-only — already eliminated by ADR-0005).

**Recommendation: elect Apache-2.0 for the whole SolidCraft dual-licensed surface.**
Reasons: (1) the **explicit patent grant** — a CAD constraint solver and B-rep-adjacent
kernel sit in patent-dense territory, and Apache-2.0 §3 is the only patent protection we
get for third-party code; MIT is silent on patents; (2) our compliance machinery for
Apache-2.0 already exists (ZCode, OCP rows: NOTICE + state-changes §4(d), §6 family
table); (3) **closure 2 forces the Apache pipeline anyway** — the truck family and
matext4cgmath are Apache-2.0-only, so a single notice pipeline covers the entire SolidCraft
surface uniformly; (4) the GPL-3.0-or-later combined-distribution path admits Apache-2.0
without friction. The cost vs MIT is modest: one NOTICE-propagation section in our
third-party notices + change markers if we ever modify their files (we already run this
playbook for ZCode). MIT remains the defensible fallback if TL2 wants minimum process for
a sketch-solver-only adoption — but then closure-2 (if ever adapted) still needs the
Apache machinery, splitting the pipeline.

MIT-only crates inside the closures (branches, generic-array, slab, …) keep their MIT
notices regardless — election applies only where the OR-choice exists.
