## 1. The rule being demonstrated (mission text, binding)

> Our document model remains the authoritative source of truth. Demonstrate how a
> constrained sketch could map into bcdoc without: a second authoritative geometry store;
> conflicting entity identity or persistence semantics; broken undo/redo or
> document-version checks; lost constraints after save/reopen; untracked geometry
> mutations; loss of correct dependency relationships after edits.

**Native Blender Curves are an upstream implementation detail.** CAD Sketcher's own store
(mesh curve attributes + `SlvsEntities`/`SlvsConstraints` PropertyGroups + its own
`serialize.py` snapshot layer — audit-upstream.md §5) is a *second document model* built
into the addon; it is **explicitly not adopted**. Our seam keeps `bcdoc` as the single
authoritative geometry store and treats the solver as a stateless compute service.

## 2. Seam design (bcdoc-first)

1. **Geometry authority.** bcdoc `Line`/`Circle`/`Arc` entities hold the geometry. The
   solver never becomes a store: every solve *extracts* a fresh slvs system from bcdoc
   values, solves, and applies results back **only via `doc.update_entity` inside a real
   `doc.transaction`** (journaled, undoable, `doc_version`-bumped — `document.py:368-405`).
   There is no second geometry cache: after apply-back, the bcdoc entities are the solved
   values (the next extraction re-reads them).
2. **Constraint records.** Constraints live in a PROPOSED bcdoc table (bcdoc/3, design
   only): a `SketchTable` of `SketchRecord`s, each `{sketch_id, workplane (deterministic
   description: origin + basis, or later a named UCS), constraints: [{kind, params,
   refs, value}]}` where `refs` address bcdoc entities **by entity id** (plus a vertex
   slot 0/1 for line endpoints). Table mutations ride the same transaction/journal/
   serialization machinery as layers/blocks/layouts today (the extension point exists:
   `document.py:84-88` table wiring). Until such a table exists, the demonstration keeps
   the records in an adapter-owned sidecar JSON — **that sidecar is the demonstrated
   gap**, not a design goal.
3. **Stateless solver service.** Each solve = fresh extract → solve → discard. This is
   forced by the measured API anyway (Phase 2a: no constraint mutation, no incremental
   path) and matches CAD Sketcher's own `curve_solver.py` rebuild-every-solve design.
4. **Identity rule.** The solver NEVER creates, removes or replaces bcdoc entities on
   apply-back. bcdoc's `update_entity` mutates fields of the SAME live object
   (`entities.py` `set_field`; `transaction.py` identity note: undo/redo restore the same
   objects), so UUIDs, handles, insertion order, layer/style references, selection and
   every other id-keyed consumer survive unchanged. Slvs helper points (junction points,
   a circle's radius param, a fixed origin) live only inside the per-solve system and are
   discarded — they are *not* document content.
5. **Value-endpoint mapping (bcdoc nuance, honest).** bcdoc lines carry endpoint VALUES;
   a "shared vertex" is coincident-by-value, not an entity reference. The extractor
   therefore materializes one slvs point per (entity, endpoint-slot) and lets the
   constraint graph's coincident constraints merge them in the solver. On apply-back,
   merged points are written to every referencing line (asserted equal within 1e-9).
   Similarly a bcdoc `Arc(center, radius, start_angle, end_angle)` maps to slvs
   (center, start, end) points by polar evaluation, and back by `atan2` + radius
   re-derivation (SolveSpace arcs have no radius variable — Phase 2a §mapping). These
   are adapter details a bcdoc/3 proposal must pin down (a per-document junction/
   param-id map is one of the recorded gaps).
6. **Failure rule (informed by Phase 2a).** On a non-`OKAY`/non-`REDUNDANT_OKAY` result
   the seam writes back NOTHING and opens NO transaction: SolveSpace's copy-solve
   semantics already leave the sketch untouched (Phase 2a §4), and the seam must
   additionally not journal, not bump `doc_version`, not fire `on_change` — a failed
   solve is a *query*, not a mutation. (For `REDUNDANT_OKAY` the seam would write back
   the solved geometry but surface the redundancy list as a document diagnostic —
   slvs's bad list is a removal-candidate/failure-point report, NOT the complete
   redundancy/conflict analysis SolidCraft provides; bcdoc diagnostics must not treat it
   as one. Phase 2a §4/§6.)
7. **Version guards.** In-process bcdoc writes have no `base_doc_version` parameter; the
   enforced guards are: one open transaction at a time (`NoOpenTransaction` on any
   mutation outside a transaction, `document.py:419-425`), snapshot rollback on failed
   transactions, and journal-application conflicts (`JournalConflict`, `document.py:493-496`).
   Optimistic concurrency (`base_doc_version`, conflict rule R1) is an AGENT-boundary
   contract already enforced in `modules/agent/bcagent/contract.py:145-156`; a solver
   service exposed to agents would go through the same boundary. Demonstrated, not assumed.

## 3. Scenario demonstrated (all steps via the REAL bcdoc APIs, read-only use)

Triangle from Phase 2a: 3 bcdoc `Line`s with rough seeds, constraint graph =
coincident(A, fixed-origin), junction coincidences (3), horizontal(l1), distance(l1)=50,
distance(l2)=45, angle(l1,l3)=60° inverse. Then: solve-1 → apply-back (transaction) →
undo/redo round-trip → save to a scratch `.bcdoc` file → fresh `Document.load` →
constraint sidecar reload → re-solve (digest equality) → stale-guard probes →
edit d1 50→40 → re-solve → apply-back → dependency-integrity assertions. Every step is a
named check in `results/bcdoc-seam.json`.

## 4. What bcdoc lacks today (gap list — PROPOSED schema items, not implemented)

| # | Gap | Proposed bcdoc/3 item | Demonstrated evidence |
|---|---|---|---|
| 1 | No constraint/sketch table — constraints cannot be document content today | `SketchTable` + `SketchRecord` (journaled, serialized, undoable like layers/blocks) | the adapter sidecar JSON is the stand-in; save/reopen must reload it separately |
| 2 | No junction/param identity — bcdoc lines have value endpoints; "shared vertex" is by-value only | optional `Point` entity references or a per-sketch junction map (id-stable) | extractor materializes (entity, slot) points; merged junctions re-written to every referencing line |
| 3 | No per-entity solver-param persistence (CAD Sketcher stores `py_data` slvs handles on entities) | NOT wanted — the stateless service makes it unnecessary; if incremental solving is ever required, a `param_ids` map inside SketchRecord (never on entities) | every solve rebuilds from bcdoc values; measured cost is the Phase 2a scale curve |
| 4 | No workplane/UCS record for sketches yet | SketchRecord.workplane (origin + basis), aligning with the UCS/OCS notes in document-model §2 | demo fixes the XY plane at the origin deterministically |
| 5 | No driving-dimension records (values + units + driven/reference flag) | SketchRecord constraints with `value` + `driven` flag (CAD Sketcher's reference-dimension gating, `curve_solver.py:335-352`, becomes a first-class record field) | d1/d2/d3 carried in the sidecar; edit = record update + full re-solve |
| 6 | No solve-status/diagnostic records | a `solve_report` session record (slvs flag + bad list) — explicitly NOT a SolidCraft-style full diagnosis (Phase 2a §4) | failure rule demonstration |

## 5. Verdict framing (no adoption decision here)

The seam is demonstrable end-to-end on today's bcdoc with zero schema changes *for the
compute path*; the durable gaps are persistence-side only (constraint records, junction
identity). The Phase 2a findings bound the service's behavior: exact fully-constrained
solves, bitwise determinism, transactional failure semantics, full-rebuild edit cost
(~O(N^2.2), 16 ms @ 200 segments on the sandbox), no incremental path. Whether that
service (vs PlaneGCS, the PAR candidate) is the right one is the TL-owned M3-entry
comparison — this document supplies the seam architecture either way.
