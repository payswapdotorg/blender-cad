# Parametric workflow in the pinned runtime — experiment C (m3-eval phase 2b)

- **Status:** evaluation record; no product code touched; the full add-on is NOT adopted
  (the mission forbids "a second CAD application inside our product"). Evidence:
  `results/parametric-workflow.json` (16 recorded steps, 13 headless-ok, every failure
  recorded with its exact error — generated by
  `scripts/runtime/parametric_workflow_probe.py`, never hand-edited).
- **Runtime:** Blender 5.2.2 LTS (`--background`) with the official CAD Sketcher v0.32.1
  linux_x64 release ZIP installed+enabled in the ISOLATED scratch user dir (Phase 1
  install; the install lives OUTSIDE the repo).

## 1. Static inventory (cited, at the pin e7db7e6)

- **Sketch lifecycle operators**: `view3d.slvs_add_sketch` (stateful pick of
  workplane/mesh-face; `operators/add_sketch.py:323`),
  `view3d.slvs_add_sketch_on_plane` (execute-based, origin planes; `add_sketch.py:414-460`),
  drawing operators `slvs_add_point2d/line2d/circle2d/arc2d/rectangle…`
  (stateful; `operators/base_2d.py:94` invoke), constraint operators
  `slvs_add_coincident/horizontal/vertical/parallel/…/distance/diameter/angle`
  (`operators/add_*.py`), `view3d.slvs_solve` (execute; `operators/solve.py:10`),
  `view3d.slvs_update` (`operators/update.py:8`).
- **The UPDATE path** (when does it re-solve?): constraint/dimension updates call
  `constraint_value_update_cb` (`utilities/solver.py:13-19`) which only sets
  `global_data.needs_solve = True`; the actual solve is DEFERRED to
  `depsgraph_update_post` → `handlers.py:186-206`: `needs_solve` is consumed,
  `curve_solver.solve_system` runs for the ACTIVE sketch, then
  `refresh_curve_geometry` forces the Geometry-Nodes topology rebuild because
  in-place point-position writes don't re-evaluate the modifier (`handlers.py:198-205`
  comment). Operators that solve do it themselves; the handler covers the
  depsgraph-driven path. Self-heal passes (external edits, undo flattening, renames,
  linked duplicates) also set `needs_solve` (`handlers.py:108-184`).
- **The 3D side at 0.32.1**: there is NO one-shot "extrude" solid operation. Extrude and
  Revolve are *stateful viewport tools* (`workspacetools/extrude.py`,
  `workspacetools/revolve.py`) driving `view3d.slvs_node_extrude/revolve`
  (`operators/modifiers.py:737+`), which attach a **live Geometry-Nodes modifier** built
  programmatically (`utilities/extrude_nodes.py:96 build_extrude_node_group`) to the
  sketch's **body** mesh object (`utilities/body.py:76 ensure_body`; body.py:1-9: "A
  sketch is a Curves object and stays pure source: no modifiers… Its geometry is pulled
  into a *mesh* object, the body"). Booleans are GN too, with the Exact-vs-Manifold
  choice (CHANGELOG 0.32.0). Arrays/Bevel/Offset/Trim/Project are all stateful tools.
  The 0.32 "parts and assemblies" layer is built on this body/part object model
  (`utilities/part.py`, `operators/add_assembly.py`).

## 3. Reusable vs host/UI-coupled separation (the adoption-relevant cut)

**Genuinely reusable algorithms / behavioral patterns** (adapt, cite, test):

| Pattern | Evidence |
|---|---|
| The solver seam design: extract-from-source → rebuild-every-solve → in-place write-back | `curve_solver.py:57-246` (+ Phase 2a: forced by the slvs API; matches our bcdoc seam design) |
| Float32-precision compare-before-write-back ("moved" means "the bytes change") | `curve_solver.py:44-54,494-530` — avoids solver-noise churn in the derived scene |
| Implied-redundancy GATING: reference dimensions never enter the solver because implied quantities "force REDUNDANT_OK and flags the group failed" (issue #674) | `curve_solver.py:335-352` — a document-model-side diagnostic policy worth porting |
| Failed-constraint MARKING for the UI (per-constraint `failed` flag) instead of a whole-sketch error dump | `curve_solver.py:329-361`, `model/base_constraint.py:114` |
| Deferred solve on depsgraph + explicit `refresh_curve_geometry` after in-place writes | `handlers.py:186-206` — the update-trigger design |
| Workplane math: fixed origin point + normal + workplane from a sketch empty's matrix; per-part XY/XZ/YZ workplanes | `curve_solver.py:90-138`, `utilities/workplane.py` |
| Sketch = pure-source Curves object; geometry realised on a separate mesh BODY carrying a live GN stack; results read via depsgraph instances | `utilities/body.py:1-9,76`, `boolean_targets.py:50-58` — a clean separation of source vs derived we already hold with bcdoc |
| Auto-constraints while drawing (alignment + joint tangency/perpendicularity, skipping when both ends anchored) | `operators/add_line_2d.py:118-160` — behavioral spec, testable |

**Host/UI-coupled — never ported** (and explicitly NOT adopted as our store):

`stateful_operator/` framework (viewport state machines, 3.2k LOC), `gizmos/` + `drawing/`
(viewport overlay/picking/snap), `ui/`, keymaps, `icon_manager`, its OWN persistence layer
(`serialize.py` + `SlvsEntities`/`SlvsConstraints` PropertyGroups on `bpy.types.Curves` —
a **second document model embedded in the addon**; our bcdoc stays authoritative,
see findings/bcdoc-seam.md §1), and the 128-bit curve-UUID attribute machinery
(`utilities/curve_data.py:28-46`) — an implementation detail of storing geometry inside
Blender Curves that bcdoc does not need.

## 4. What this means for the M3 decision (evidence only)

The upstream workflow is fully reproducible *mechanically* without any of its UI: creation
via an execute operator or 3 lines of model API, constraints as records, solve as a
stateless call, edits as value changes + re-solve, and 3D realisation as a live GN
modifier on a derived body — i.e. the addon's architecture validates the same
source-vs-derived split our bcdoc seam uses (BCD seam: geometry writes are journaled
document mutations; upstream: sketch object stays pure source). The parts/assemblies layer
is beyond M3 scope. No verdict here — TL-owned.
